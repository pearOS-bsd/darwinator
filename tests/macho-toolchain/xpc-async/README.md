# xpc-async

`asynctest`: an XPC client that sends a message with `xpc_connection_send_message_with_reply` (an asynchronous reply handled by a block) to `com.apple.coreservices.launchservicesd` (the `lsd-stub`).  Build: `sh build.sh OUT` (`ASYNCTEST_CFLAGS=-DASYNCTEST_WAIT=6` waits 6 s first, for a debugger).

It reproduced the crash that every Apple program that waits for an asynchronous XPC answer had here: SIGSEGV in `_xpc_connection_call_reply_async` (libxpc), reading `0x98(%rsi)` with `rsi == NULL`.  Cause: libxpc keeps the context of a call as the guard of the reply port (`mach_port_guard`, or the context of `mach_port_construct`) and reads it back from the trailer of the answer (`msgh_context`, at 0x34 of the trailer: `__xpc_mach_msg_get_context`).  `mach_port_guard` did nothing and the trailer had zeros.  Now the port keeps it (`kport.context`: construct, guard/unguard, mach_port_set/get_context) and the trailer has it (60 bytes for the context, 64 with the filter policy id, 68 with the labels).  Also fixed on the way: EV_UDATA_SPECIFIC is given back on machport events and errors come back with the flags of their change.
